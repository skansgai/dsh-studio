## 三、dsh 侧的变化（0.1.2-rc.1 → 0.1.5-rc.2）

我们 0.3.1 适配的是 0.1.2-rc.1，dsh 已经跳到 **0.1.5-rc.2**，且有**破坏性变更**：

| 变更 | 对我们的影响 |
|---|---|
| 会话数据格式升级 **V3**，不支持降级读取 | 会话相关功能需重新验证 |
| Session 生命周期改造 + **session 独占锁**（同一 session 至多一个进程持有） | 直接影响「复用外部实例」策略，需重新评估 |
| **原 Detail 面板已移除**，右侧 Sidebar 改多标签/分栏/全屏 | 我们注入「通用设置」的 DOM 锚点可能已变 |
| **Web 插件面板 API 正式化**：`sidebar.panellist` / `main` 注册全局面板 | ⭐ 这是**正路**：不再 DOM 注入 |
| Web 顶栏新增「在应用中打开」 | dsh 自己就能唤起 IDE，我们的「打开方式」价值被削弱 |
| Web 支持上传任意类型文件 + 多格式预览 | 自建文件预览没必要做了 |
| 会话统计支持**精确 Token 用量与缓存命中** | 可直接读出来展示 |
| 出站请求遵循 `HTTP_PROXY`/`HTTPS_PROXY` 等 | 代理环境下更稳 |
| `dsh plugin --profile web add <包名>` | ⭐ 插件可被正式安装，不用改 DOM |

**新出现的包**（可被插件利用）：
`dsh-acp-app`（ACP stdio 服务）、`dsh-skill`（技能注册表）、`dsh-goal`（目标状态）、`dsh-webhook`（webhook 运行时）、`dsh-session-stats` / `dsh-token-meter`（用量）、`dsh-client-ui-*`（整套 UI 都是插件）。

## 四、需求清单（按「不做会不会死」排序）

### P0 · 生存级（不做就会持续流失用户）

**1. 干掉首启 284MB / 14 分钟（客户侧是转化杀手）**

实测体积（2026-09-11）：

| | 插件包大小 | 客户首次可用时间 | 落盘 |
|---|---|---|---|
| 我们 33569 | **0.1 MB** | **约 14 分钟**（`npx` 拉全量） | 294 MB |
| 竞品 33555 | **40.7 MB**（内置运行时） | 秒级 | ~120 MB（估） |
| 竞品 33820 | 1.8 MB（按需下载）；**0.1.3 曾内置 93.4 MB，之后回退** | 1–5 分钟（视网络） | 按需 |

- 市场单插件上限 **400 MB**，40–90 MB 只占 10–22%，不是约束。
- 我们的 294 MB 里 **dsh 本体只占 39 MB**；其余是 `@img` 46M（图像原生库）、`@opentelemetry` 31M、
  `node-pty` 27M、`openai` 15M、`@google` 14M、`@aws-sdk` 等——**大部分可裁**。
  也就是说「内置」并不等于 294 MB，竞品用 40.7 MB 就做到了。
- 14 分钟的首次等待直接吃掉试用转化窗口；而 33820 从 93.4MB 回退，说明**体积要控制在 40 MB 上下**，
  过大反而会反噬更新体验。

→ 推荐方案：**内置精简运行时（基线）+ 运行时独立热更新 + 保留逃生口**
  - 内置一份裁剪过的基线运行时 → 首次可用时间从 14 分钟降到秒级，离线/内网也能用；
  - 启动时后台检查新版运行时，下载到用户目录（与插件版本解耦）→ 不受插件发版节奏限制，dsh 迭代快也不怕；
  - 设置页保留「使用内置 / 使用全局 dsh / 自定义命令」三选一（现有配置项即可承接）。

**✅ 可行性已实测（2026-09-11）**：dsh 依赖闭包 457 个包、210.7 MB，压缩 54.6 MB；
裁掉 sourcemap / `.d.ts` / 文档 / 测试后 **35.5 MB**——与竞品 33555 的 40.7 MB 基本持平，
远低于 400 MB 上限。**体积不是障碍。**
详见 `docs/design-bundled-runtime.md`（含构建链路、分层结构与实施顺序）。

**2. 原生 Diff 审查**
agent 改了文件，用户需要在 IDE 的原生 diff 里看改动、逐处接受/拒绝。两个竞品都做了。这是「敢不敢让 agent 动我代码」的信任基础。
→ 方案：监听 dsh 的 edit/write 工具事件（或解析会话日志），在 IDE 里打开 `DiffManager` 对比。

**3. dsh 0.1.5 兼容**
破坏性变更已列出。不做的话，用户升级 dsh 后插件直接不可用。
→ 方案：真机跑一遍 0.1.5-rc.2，定位设置面板锚点变化；把「已验证的 dsh 版本范围」写进插件并在启动时校验。

**4. 端口自愈**（0.3.1 就排了 P1，一直没做）
端口被占用 → 自动换端口 + 提示。低风险、高感知，直接减少「启动失败」类差评。

### P1 · 追赶级（补齐竞品已有能力）

**5. 工具调用审批在 IDE 内呈现** — 审批卡片不该只在网页里。
**6. IDE 上下文持续同步** — 当前活动编辑器 / 已打开标签页，供 `@` 引用；不能只在「发送那一刻」查一次。
**7. 项目隔离 profile** — 每个项目独立 dsh profile，避免跨项目插件/配置串味；配「恢复默认」兜底。
**8. 任务完成 / 需要审批 / 需要输入 → IDE 通知** — 长任务跑着时用户可以去做别的。
**9. Token 用量与成本展示** — dsh 已提供精确统计，接出来即可。

### P2 · 差异化（我们独有的机会）

**10. 守住最广的 IDE 兼容面（231.0+）** ⭐
竞品分别从 241.0 / 243.0 起。Android Studio 用户普遍升级滞后，2023.1–2024.2 区间**只有我们能用**。这是当前最硬的差异化，值得作为卖点写进市场文案，并在 CI 里跑兼容性验证兜住。

**11. 运维可观测性做深** — 我们已经是三个里唯一有「启停 + 状态栏 + Server Log」的。可以再加：多实例管理、日志一键导出、诊断报告生成（环境 + 版本 + 端口占用 + 日志打包）。这是「出了问题能自救」的能力，正好补竞品短板。

**12. ACP 接入：`dsh --profile acp` → JetBrains AI Chat** ⭐
dsh 提供 `dsh-acp-app`（ACP v1，JSON-RPC over stdio），JetBrains AI Assistant 支持通过 `~/.jetbrains/acp.json` 接入自定义 ACP agent，**且不需要 AI 订阅**。
→ 价值：dsh 变成 AI Chat 里的原生 agent，拿到原生 diff / 审批 / 文件树，彻底摆脱 webview 与 DOM 注入。
→ 注意：已有第三方 `dsh-acp-gateway` 在做网关；且 ACP 仅在装了 AI Assistant 的 IDE 可用（老 Android Studio 可能没有），所以**与 webview 并存**而非替换。

**13. 用 dsh 官方插件机制替代 DOM 注入** ⭐
`dsh plugin --profile web add <包名>` 可以正式安装插件；`dsh-client-ui-*` 说明 dsh 的整套 UI 都是插件组成的。
→ 把「背景图卡片」这类注入改造成一个真正的 dsh 插件包，走 `sidebar.panellist` / `main` 扩展点。
→ 这是**根治**：0.3.x 那一串「关于」页 bug（版本号闪没、内容漏成窄列）的根因就是 DOM 注入被 SPA 重绘冲掉。

### 明确不建议做

| 不做 | 理由 |
|---|---|
| 继续 DOM 注入导航/面板类节点 | 已验证修不好（结构性缺陷），且有官方扩展点可走 |
| 自建文件预览器 | dsh 0.1.5 已有 Sidebar 多格式预览（Markdown/代码/HTML/PDF/图片） |
| 完整的 dsh 插件市场界面 | dsh 自带插件页，社区已有第三方 registry（dsplugin.app） |
| 背景图这类纯装饰 | 不构成任何选型理由，别在上面花时间 |

## 六、需要你拍板的问题

1. **运行时策略**：这个问题不该问「我们能不能接受体积」，而该问「哪类客户会因为这个放弃」。
   实测结论：14 分钟首启等待是**试用转化杀手**（决定性人群）；40 MB 内置在市场 400 MB 上限内、
   且竞品已验证客户接受；93 MB 级别的内置则可能反噬更新体验。
   建议按「内置 40MB 级基线 + 运行时独立热更新」推进，而不是继续让客户 `npx` 等 14 分钟。
   —— 需要你确认的是：**是否接受为裁剪/打包运行时增加一条构建链路**（工作量，而非体积）。
2. **IDE 兼容面**：要不要明确把「支持 2023.1+」当卖点投入验证成本？竞品都放弃了这一区间。
3. **ACP 与 webview 的关系**：并存（推荐）还是逐步替换？
4. **DOM 注入改造的时机**：现在就迁到官方插件机制，还是等 0.1.5 兼容做完再说？
5. 要不要我建一个**每日自动跟踪**（竞品版本 / dsh 新版本 / 市场评论），有变化就提醒你？
